# Embedded Sidecars

In-tree sidecars under `sidecars/channel/*` and `sidecars/tool/*` ship inside the baybo binary as zstd-compressed JS bundles. `crates/gateway/build.rs` invokes the package's `bundle` script (channels: `bun build --target=bun --minify`; tools: `esbuild`), zstd-compresses the result + any aux files, and emits `$OUT_DIR/sidecar_assets.rs`. At boot, `SidecarRuntime::install` materialises everything to `$XDG_CACHE_HOME/baybo/sidecars/<name>-<hash>/{bundle.mjs, <aux...>}` — hash-keyed so an upgrade never overwrites an old bundle, and the janitor sweeps stale `<hash>/` dirs once a day (live-set allowlist + 7d mtime guard).

- **Build prereqs**: `pnpm install` populates `node_modules`, and `bun` must be on `PATH` (channel sidecars; override with `BAYBO_BUN_BIN`). Tool sidecars run under `node` (override with `BAYBO_NODE_BIN`). Missing the install degrades to `cargo:warning=…` with empty embedded assets — the build still succeeds, the supervisor logs "embedded sidecar runtime unavailable". Set `BAYBO_REQUIRE_SIDECARS=1` for release builds to hard-fail on packaging failures.
- **Why bun for channels**: with `--target=bun`, bun substitutes its own polyfills for `ws` / `node-fetch@2` / `silk-wasm`, dodging three node + esbuild traps (DEP warnings, esbuild minifier deadlocking `bot.init()`, and `silk-wasm`'s `__filename` reference in ESM). Tool sidecars don't ship those packages and run under node directly.

Every sidecar self-declares an `baybo.domain` in its `package.json` (`channel`, `tool`, …). Domain identifies the family; the per-package name identifies an individual sidecar inside it. Constants live in `baybo_gateway::sidecar::domains`. **Build-time enforcement**: a missing or invalid domain (must match `[a-z0-9_]+`) is a hard `cargo build` error — new sidecars can't silently default into the wrong family.

Adding a new sidecar:
1. Pick a directory (`sidecars/channel/<name>/` or `sidecars/tool/<name>/`) — the `sidecars/*/*` glob in `pnpm-workspace.yaml` picks it up automatically.
2. `package.json` declares `"baybo": { "domain": "channel" | "tool" | ..., "kind": "mcp_server"? }`.
3. For a new family, add a `domains::YOUR_DOMAIN` constant in `crates/gateway/src/sidecar/assets.rs` and iterate it from whichever supervisor / route / CLI dispatches that family.
4. For a new tool-domain MCP server: also add an `*_mcp_profile(...)` builder in `crates/tools/src/mcp/profile/<name>.rs` (primitive args so `baybo-tools` stays free of an `baybo-config` dep) and append an entry to the array literal in `baybo_gateway::collect_profiles` (`crates/gateway/src/sidecar/embedded_mcp.rs`) — `runtime::build_managers` stays unchanged.

Existing dispatch:
- `baybo channel list/add` filters `runtime.names_in_domain(domains::CHANNEL)`.
- `SidecarSupervisor` (channel restart loop) iterates `domains::CHANNEL`.
- `baybo_tools::mcp::embedded_servers(&profiles)` consumes the `EmbeddedMcpProfile` list from `baybo_gateway::collect_profiles` (`crates/gateway/src/sidecar/embedded_mcp.rs`); the resulting servers are handed to `runtime::build_managers` (today: just browser when `browser.enable=true`).

## Media side-channel (`/v1/blobs/*`)

Non-text media — a file the agent sends, a screenshot a tool produced, an image a user uploads — **never rides the channel WebSocket**. The bytes live in the gateway's content-addressed `BlobStore` (`crates/store/src/blob.rs`); the wire carries only a `WireAttachment` reference (`kind`, `blob_id`, `mime_type`, `size`, `filename`, `duration_ms`). A 100 MiB file is a tiny frame, and a slow media transfer can't head-of-line-block unrelated traffic on the same multiplexed connection. Bytes move over a separate channel-token-authenticated HTTP route, `POST/GET /v1/blobs/*` (`crates/gateway/src/channel/blobs.rs`), mounted under the same auth middleware as `/channel-ws`.

`BlobStore::put_stream` hashes chunks on the fly, writes a temp file, then renames to `<blobs_root>/<sha256[0..2]>/<sha256>`, so identical content dedups to one physical file. Each `put` still mints a **distinct, unguessable `blob_id`** (`"sha256:<hex>.<read_token>"`, see `SHA256_PREFIX`) — the id *is* the read capability, so "same bytes" ≠ "same id" and sharing an id delegates read access. The 100 MiB ceiling (`MAX_BLOB_BYTES`) is enforced incrementally during upload and mirrored by axum's `DefaultBodyLimit`.

**Outbound (agent → user).** A tool stages bytes and delivers a *reference*, never the bytes: `AttachFile` (`crates/tools/src/builtin/attach_file.rs`) streams the file through `put_stream`, then returns `ToolOutput::WithAttachments { text, attachments: [ContentBlock::File { blob, .. }] }`. The agent loop accumulates every turn's `WithAttachments` media and folds it into the **final assistant message** — the same blocks land in the persisted `session_messages` row and in `OutgoingMessage.content`, so the file survives a reload instead of existing only as a live push. `agent_output_to_frame`'s `split_content` → `stat_attachment` (`crates/gateway/src/channel/adapter.rs`) then turns each media `ContentBlock` into a `WireAttachment` (the `stat` fills `size` / `mime`) on `Frame::Message.attachments`. The sidecar pulls the bytes back: `fetchBlob` (`sidecars/sdk/channel-ts/src/blobs.ts`) does `GET /v1/blobs/<id>` with the `BAYBO_CHANNEL_TOKEN` bearer (base URL derived from `BAYBO_CHANNEL_URL`), and `sendTelegramAttachment` (`sidecars/channel/telegram/src/media/outbound.ts`) wraps them in a grammy `InputFile`, dispatching to `sendPhoto` / `sendVideo` / `sendVoice` / `sendAudio` / `sendDocument` by `kind` + MIME. The gateway's `download` handler streams from `BlobStore::open` (no server-side buffering); the telegram side deliberately buffers via `fetchBlob` rather than `fetchBlobStream` because grammy's multipart on bun chokes on web streams (and the Bot API caps at 50 MB anyway).

Attachments arrive **only on the turn's terminal `Frame::Message`**, never mid-turn — a file staged at tool-step 2 of a ten-step turn surfaces when the reply does. That is the price of durability: the media block rides the one assistant row the loop persists, so a client that reconnects or cold-starts rebuilds the same bubbles from `transcript_attachments` (`crates/gateway/src/api/admin/chat.rs`) with no special-casing. Sidecars deliver it from `Channel.onMessage`: `BotChannel` takes the `sendMedia` path when `msg.attachments` is non-empty, shipping the reply text as the caption in one platform call (Telegram splits the text back out when it exceeds the 1024-codepoint caption cap). Clients render each attachment as its own bubble stacked with the reply prose; surfaces that can't render media (the TUI) drop the attachments and keep the text. One blob reaches the reply at most once: the loop dedups the turn's staged media on the blob's **SHA-256 digest**, never on its `blob_id` — each `BlobStore::put` mints a fresh read token, so `AttachFile` called twice on one path yields two distinct ids for the same bytes and an id-keyed dedup would wave both through. A turn that never reaches a clean final response — cancelled, errored, or budget-exhausted — drops its staged attachments: the blob stays in the store but no row references it, so nothing half-delivered can survive a resync. A **subagent** hoists media onto its own final message (visible if you open the subagent's session) but the parent boundary is text-only (`result_text()`), so it cannot leak into the parent's user channel.

**Inbound (user → agent).** The mirror image: a sidecar `POST /v1/blobs` to stage a platform attachment (`uploadBlob`), then references the returned id in the `attachments` of the `Frame::Message` it sends upstream. Uploads run a pairing gate first — `authorize_upload` checks the `(channel_type, bot_id, user_id)` triple (from the `x-baybo-bot-id` / `x-baybo-user-id` headers) against `PairingService`, so an unpaired peer can't cause durable 100 MiB writes; TUI / web / tool-sidecar uploads are session-scoped and bypass it.

## Browser tool sidecar (`sidecars/tool/browser`)

Thin wrapper around Google's [`chrome-devtools-mcp`](https://github.com/ChromeDevTools/chrome-devtools-mcp) (CDDM, version-pinned in `sidecars/tool/browser/package.json`). Spawned by `McpReconciler` over stdio MCP; CDDM's core tools (`navigate_page`, `click`, `take_screenshot`, `evaluate_script`, `take_snapshot`, `list_console_messages`, network observers, …) surface as `browser/<tool>` to the LLM. We disable several CDDM categories and tools to keep the agent's tool-list footprint small: `extensions` (mutates the persistent profile), `emulation` (`emulate` / `resize_page` — viewport is fixed at sidecar boot, and `emulate`'s schema is a ~1.2 KB enum we rarely need), `performance` (multi-second traces); plus name-level overrides for `lighthouse_audit`, the `webmcp` pair (`list_webmcp_tools` / `execute_webmcp_tool` — require host-side WebMCP support no normal page exposes), and `take_memory_snapshot` (debug-only). The proxy's `BLOCKED_TOOLS` set in `sidecars/tool/browser/src/server.ts` is the source of truth for name-level overrides; category flags live in `buildArgs`. One additional in-process tool — `browser/read_page` — wraps Mozilla Readability + Turndown for clean Markdown extraction.

**Opt-in**: `baybo.json:browser.enable=false` by default — when off, the bundle stays inert in the binary and `browser/*` tools never appear. All operator-facing knobs live on the `BrowserConfig` struct (`crates/config/src/browser.rs`); the wrapper itself reads `BAYBO_BROWSER_*` env vars only as internal gateway↔child plumbing.

**Not offered to a card's run.** The profile sets `trigger_scope: SharedWorkspace` (`crates/tools/src/mcp/profile/browser.rs`), so `ToolRegistry::tool_definitions_for_session` leaves `browser/*` out of an issue run — and the executor refuses one that gets named anyway. A user conversation, a board lead's planning session and a cron fire all keep it. The line follows the isolation that already exists: those three work the shared workspace, while an issue run is cut its own checkout, and the browser is one process-wide Chrome with one profile and one cookie jar (see the security posture below) — there is no unshared instance to hand it. It also takes 24 tools / ~19 KB off the tool block of every request a run makes; the eleven-day sample behind the deferral note above found every `browser/*` call came from board work, and all of them failed.

**Chrome binary**: auto-downloads Google Chrome for Testing 'stable' to `$XDG_CACHE_HOME/baybo/browser/chrome/` on first use via `@puppeteer/browsers` — non-blocking (the MCP server connects immediately so the LLM sees the full tool list; calls during install get a synthetic "preparing, N% complete, retry" response via `GuardingTransport`). Pin a specific Chrome via `browser.chrome_path`. Pre-warm air-gapped: `pnpm --filter @baybo/tool-browser run install-chrome`.

**The browser starts on first use, not at gateway boot.** `main()` brings up the MCP surface only: `tools/list` is answered in-process, so the LLM sees every browser tool immediately, while `state.phase` sits at `idle` and `GuardingTransport` parks any `tools/call` with a "launched on first use, retry shortly" reply. Every parked call calls `ensureBrowserStarted()`, which owns the "is a start needed" question by itself — the transport does not gate it on a phase. It brings up the target, mutates the caller-owned `args` to point at it, seeds the `HintContext` mount fields, flips the phase to `ready` and only then wires the watchdog. Deferral is what makes the container churn proportional to actual browsing rather than to gateway restarts — an eleven-day sample of this workspace had 7 `browser/*` calls against 88 boots.

**A bring-up that throws is retried on the next browser tool call.** `browserStart` latches only while a start is in flight; a `resolveBrowserTarget` throw releases it again. Latching the failure permanently is a real trap and not a hypothetical one: the escalate → `process.exit(1)` → reconciler-respawn path lives inside the watchdog, and the watchdog is not constructed until the start succeeds — so one transient docker or DNS hiccup on the first `browser/*` call would disable browsing for the whole life of the process with nothing able to notice. A failure *after* the start adopted a container is deliberately **not** retried: starting over would orphan that container, and the next boot's sweep skips containers whose owner pid is still alive.

The gate is load-bearing, not cosmetic: CDDM caches its browser in a module-level singleton guarded on `browser?.connected` alone and **discards every argument on a cache hit**, so a call that reached CDDM before `args` was final would pin the wrong mode permanently. `GuardingTransport` intercepting *every* `tools/call` while `phase !== "ready"` is the only thing standing between those two facts — do not weaken it. `hintCtx.mode` is seeded from the configured mode (not left undefined) because `augmentToolDescriptions` writes mode-specific namespace notes into the tool descriptions at `tools/list` time, which happens before the browser exists.

**One home for "which mode is this".** `configuredMode()` reads the env once, in `main()`, and returns a `ModeSelection` carrying whatever that choice needs to act on (the `cdp_url` string, the macOS `docker.enable` override flag). `resolveBrowserTarget` switches on that selection and the watchdog's healer choice reads it — neither re-derives the branch from `BAYBO_BROWSER_DOCKER_*`. The single exception is the runtime degradation inside `resolveBrowserTarget`: docker that will not spawn falls back to host-headless, which is a fact about this boot rather than about the configuration, and is why `BrowserTarget.mode` (not `ModeSelection.mode`) is what `hintCtx` and the docker healer branch end up holding.

**Auto-fontconfig**: `<workspace>/work/.fonts/` is always pinned as a Chrome fontconfig `<dir>` (synthesised temp `fonts.conf` + `FONTCONFIG_FILE` env). Drop a CJK / icon font there and Chrome picks it up next restart. macOS no-op (Chrome uses Core Text).

### Browser watchdog (`src/watchdog.ts`)

Two layers supervise the browser, because one process death and one browser death are different events.

The **gateway** owns the process: `McpReconciler` (`crates/tools/src/mcp/reconciler.rs`) probes every embedded MCP server on a 5s tick and respawns a child whose stdio pipe broke, with 500ms→30s backoff. That probe is a `tools/list`, bounded by `EMBEDDED_PROBE_TIMEOUT` so a *hung* child can't stall reconciliation for every other MCP server behind it in the same sequential loop.
The gateway retains and awaits the reconciler task during shutdown, but only up to the runtime's shared shutdown deadline; cancellation races an in-flight reconciliation tick so a hung initialize or tools exchange cannot block teardown. The stdio transport gives the browser child 27 seconds to finish its own 25-second cleanup deadline before escalating to SIGKILL. The browser sidecar treats stdin EOF as the same shutdown edge as SIGINT/SIGTERM. That second edge is the crash backstop: if the gateway disappears before Rust can run its async cleanup, closing the stdio pipe still makes the sidecar stop its browser/container and exit instead of being reparented to PID 1.

The **sidecar** owns the browser, because the gateway structurally cannot see it: our proxy answers `tools/list` in-process, so Chrome can be gone for hours while the MCP server looks perfectly healthy and every `browser/*` call returns "Could not connect to Chrome". The watchdog probes the browser itself every 30s and follows one detect → repair → escalate ladder, with per-mode behaviour plugged in via `BrowserHealer`:

| mode | liveness probe | repair |
| --- | --- | --- |
| `host` | `list_pages` through CDDM | SIGKILL a hung Chrome (found via the profile's `SingletonLock` target), clear stale `Singleton*` locks, let CDDM relaunch |
| `docker` | `GET <cdpUrl>/json/version` | force-remove the container, sweep, respawn, repoint `args.browserUrl` at the new ephemeral port |
| `cdp_url` | `GET <cdpUrl>/json/version` | none — the operator owns that Chrome; report and keep probing |

Load-bearing details:

- **It stands down when the browser is in use.** Live traffic proves liveness better than a probe, and CDDM serialises every tool call behind one mutex — a probe fired mid-call would queue behind it and then time out against a healthy browser. In every mode the watchdog is not even *constructed* until the browser starts, which is itself deferred to the first tool call.
- **Two consecutive failed probes** are required before repair runs. Docker recovery is destructive (the container, and every tab open in it, is replaced), so one transient loopback error must not trigger it.
- **`recover()` proves itself** with an end-to-end call rather than resolving optimistically — a respawned container whose CDP port answers can still be unreachable through the puppeteer connection CDDM has cached.
- **Escalation is `process.exit(1)`.** After 3 failed recoveries the sidecar exits (stopping its container first) and lets the reconciler respawn it, which re-runs the full boot sequence — lock clearing, container sweep, Chrome install. Full re-initialisation already exists at boot and doesn't need a second implementation inside the watchdog. `cdp_url` mode never escalates: exiting would crash-loop against the reconciler while fixing nothing.
- **The phase flips off `ready` during repair**, which is what makes `GuardingTransport` answer an agent's `tools/call` with the healer's own outage text instead of letting a raw puppeteer `Target closed` reach the model. The wording is per-mode (`BrowserHealer.outageText`) because the honest answer differs — two modes are restarting the browser, `cdp_url` is only waiting for someone else to. The docker respawn deliberately runs with its own `onPhase` that logs rather than assigning `state.phase`: reusing the boot callback would overwrite `recovering` with `docker-building-image` and tell the agent its browser is in first-time setup when what actually happened is a mid-session crash.
- **An outage is logged once, not once per tick.** The gateway's stderr drain demotes everything past `MCP_STDERR_INFO_LINE_BUDGET` (300 lines/spawn) to `debug!`, so a `cdp_url` outage that logged every cycle would silence this sidecar's real warnings for the rest of the process.
- **Shutdown quiesces the watchdog** rather than just setting a flag. A docker repair can be several minutes long (`docker rm` → image resolve → `docker run` → CDP wait), and exiting under it would orphan the container `spawnContainer` is about to create — the next-boot sweep skips containers whose owner pid is still alive, so nothing would ever reclaim it.

**Chrome install is retried** (4 attempts, 15s/30s/45s backoff) before `phase` goes to the terminal `failed`. A boot that landed in a network blip used to wedge `browser/*` until the operator restarted the gateway, and `failed` is the one phase the watchdog can't help with — there is no browser to probe.

**Editing CDDM interaction — two traps.** CDDM caches the browser in a *module-level* singleton guarded on `browser?.connected` alone: on a cache hit it returns the cached instance and discards every argument. So (a) mutating `args.browserUrl` only lands once the old connection has actually dropped, which is why docker recovery force-removes the container first, and (b) never switch *modes* (launched ↔ connected) at runtime — the guard ignores mode entirely and would hand back the wrong browser. Reaching for CDDM's `closeBrowser` to force the issue does not work either: it isn't exported from the package entry, and a deep import gets inlined by esbuild as a second module instance with its own singleton (the `bayboResolveCddm` plugin only externalises the exact specifier `chrome-devtools-mcp`).

### Security trade-offs (deliberate)

Shape what the agent can be safely told to do — not bugs but load-bearing:

- **No per-Baybo-session isolation**. All sessions in one Baybo process share the default browser context/profile unless an agent explicitly passes `isolatedContext` to `new_page` (CDDM creates a Puppeteer `BrowserContext` per name); Baybo does not wire a per-session context automatically. Concurrent sessions see each other's cookies. Docker mode does not restore isolation.
- **No in-sidecar SSRF guard**. CDDM doesn't gate navigation to RFC1918 / loopback / cloud-metadata. With approvals also off, the LLM can navigate to `http://169.254.169.254/...` un-prompted. Treat `browser/navigate_page` to a non-vetted hostname the way you'd treat a `WebFetch` to that host. **Docker mode shifts the target set rather than shrinking it**: the container's own loopback is nearly empty, but `host.docker.internal` and the bridge subnet are reachable names for the host, so services the operator believed were loopback-only are in range whenever the host firewall admits `docker0`.
- **`<workspace>/work` is readable by the browser** (`docker.mount_work_dir`, default on). A page cannot read it — `file://` origins can't fetch other `file://` URLs, and remote origins can't touch `file://` at all — but the *agent* can navigate to any path under it and `evaluate_script` the contents out. That is not new capability (the agent already has filesystem tools for the same directory), but it does mean a prompt-injected agent has a second route out. The mount is read-only, so nothing there can be modified through the browser. Set `false` to remove it.
- **No per-call approval gate**. The browser MCP profile declares `capabilities = []` (`crates/tools/src/mcp/profile/browser.rs`), so the agent loop's pre-execute approval prompt never fires for `browser/*`. Add HITL gateway-side, not in the MCP layer.
- **Wide tool surface**. `evaluate_script` runs arbitrary JS in the page and is ungated. (Performance trace, lighthouse audit, and webmcp tools are hidden by the wrapper, but the rest of CDDM's surface — including arbitrary JS eval — is live.)
- **DNS-rebinding window**. CDDM runs no sidecar-owned resolver — the agent has no checkpoint between resolution and CDP commands.

### Docker mode (`browser.docker.*`)

Opt-in via `browser.docker.enable=true`. Spawns a debian-slim container running consumer Chrome behind Xvfb and connects via CDP. Headed Chrome (no `HeadlessChrome` UA) is the point — many anti-bot stacks reject the headless profile. Any docker failure (daemon down, perms, …) transparently falls back to host-headless; boot never breaks on a missing daemon. **macOS exception**: force-disabled on darwin (Docker Desktop's hidden Linux VM defeats the "real native Chrome" point — wrapper logs an explicit "ignored on macOS" line).

- `docker.cdp_url`: escape hatch — when set, skips every docker interaction and connects directly to a pre-existing Chrome (k8s, docker-compose, remote host).
- `docker.web_vnc_port`: opt-in noVNC observability (`x11vnc` + `websockify` on the configured port). Open `http://127.0.0.1:<port>/vnc.html` in any browser. **No password, loopback-only by design** — for remote access use `ssh -L`. Don't publish on a public interface.
- `docker.image_tag`: override the deterministic `baybo-browser:<sha256(Dockerfile+entrypoint)[..12]>` tag and skip the on-first-boot build (air-gapped registries).
- `docker.mount_work_dir` (default `true`): bind-mount `<workspace>/work` read-only at `/data/work`. See "Namespaces" below — without it every `file://` URL naming a host path fails.
- `docker.memory_limit_mb` (default `4096`, `null` for uncapped): `--memory` / `--memory-swap` on the container. Swap is disabled deliberately (both set to the same value) — swapping a browser trades an honest OOM for minutes of thrash that reads as a hang. The cap buys **containment, not recovery**: the cgroup OOM killer picks within the container and Chrome renderers carry `oom_score_adj=300`, so a tab dies while the browser process and its CDP endpoint survive — the watchdog probes liveness, correctly sees a healthy browser, and replaces nothing. The agent observes one unresponsive page; the host observes nothing. Detecting that would need a CDP `Target.targetCrashed` subscription the watchdog does not have. The container also runs `--pids-limit=8192`; note that writes cgroup `pids.max`, which counts **threads** — a measured 7-tab browser sat at 386 tasks across 29 processes, so a limit sized as if it counted processes would strangle a normal working set.

**Namespaces — the two failures this mode manufactures.** The container has its own network and mount namespace, and Chrome reports both mismatches as ordinary `net::ERR_*` codes that read like something else entirely:

| the agent asks for | Chrome says | what actually happened |
| --- | --- | --- |
| `http://127.0.0.1:<port>` | `ERR_CONNECTION_REFUSED` | that loopback is the *container's*; a host-side server is in another namespace |
| `file:///<host path>` | `ERR_FILE_NOT_FOUND` | the path isn't in the container's mount set — nothing to do with the file existing |

Mitigations, in the order they fire:

- **`/data/work`.** `<workspace>/work` is bind-mounted read-only, so an artefact the agent just wrote is reachable as `file:///data/work/<rel>`. Read-only on purpose: the agent has filesystem tools for writing, and it keeps page JS from reaching back into the workspace through a `file://` origin.
- **`host.docker.internal`.** Published via `--add-host …:host-gateway`, gated on Docker ≥ 20.10 (`supportsHostGateway`) because an older daemon rejects the whole `docker run` and would silently demote the operator to host-headless. The alias is not only a convenience: on a host whose DNS is rewritten by a proxy, the *unconfigured* name resolves to a decoy that accepts connections and returns nothing, so an `/etc/hosts` entry is what makes the failure honest. Reaching the host still needs the server bound to `0.0.0.0` **and** a firewall that admits the bridge subnet — neither is visible from the error.
- **Error annotation.** `src/net_hints.ts` appends the explanation above to any `net::ERR_*` result before it reaches the model, remapping a work-dir path to its `/data/work` form when it can. `isError` is left alone — the watchdog's liveness accounting keys off it.
- **Tool description.** `src/tool_notes.ts` amends `new_page` with the same facts up front, so the first attempt is right rather than the second.

**Tab backstop (`MAX_PAGES = 128` in `src/page_budget.ts`, deliberately not configurable).** Nothing upstream reclaims a page: CDDM opens one per `new_page` and closes one only when the model calls `close_page`, with no TTL, LRU, or cap. One sidecar serves every session, agent and subagent in the process, so a tab outlives the agent that opened it and the count falls only when the browser is replaced. Left alone the ratio runs about 23 `new_page` per `close_page`, and each live tab is a Chrome renderer holding on the order of 100 MiB. `src/page_budget.ts` evicts least-recently-used tabs before a `new_page` that would exceed the cap, where "recently used" is measured from proxy traffic (any call carrying a `pageId`, plus the page `new_page` returns). Page ids are a monotonic counter in CDDM, so closing one never renumbers the others. Eviction is always announced in the tool result — a tab that vanished silently would resurface as an inexplicable "No page found" on the next call.

The ceiling is a compile-time constant with no `baybo.json` knob on purpose. At 128 it sits far above any plausible working set, so reaching it means something has already gone wrong; a knob would only invite raising it past the point where the container memory limit does the stopping instead. Tabs the agent closes itself still cost nothing, and `close_page` remains the intended discipline — the backstop is what happens when that discipline fails.

Three details the cap cannot work without, each of which fails silently:

- **`experimentalStructuredContent` must be passed** to `createMcpServer`. CDDM attaches the machine-readable page table only under that flag, and it is off by default when CDDM is driven programmatically — only its own CLI sets it. Without it `list_pages` returns prose alone, `listOpenPages` throws on every call, `makeRoomForOne` swallows that and reports "nothing evicted", and the cap is a no-op with every unit test still green (they inject fakes). The boot summary reports `structured_content=on` for exactly this reason, and `test/page_id_routing.test.mjs` asserts it. The proxy strips `structuredContent` back off on the way out, so the model doesn't get a second copy of every snapshot and network log.
- **`new_page` is serialised.** Enforcement is a check-then-act across two awaits, the MCP SDK dispatches request handlers concurrently, and the gateway shares one connection across every agent. Ungated, N concurrent `new_page` calls each read the same pre-eviction count, each pick the *same* LRU victim, and N-1 get "No page found" for a tab they never owned — while the cap overshoots by N-1.
- **`close_page` refusals are detected from the page list, not `isError`.** CDDM swallows its own "the last open page cannot be closed" into a response line without setting `error`, so a refusal arrives looking exactly like a success.

**Disk.** Chrome's HTTP cache is capped at 256 MiB via `--disk-cache-size` in both modes (the value is passed to the container as `DISK_CACHE_SIZE`). The profile is bind-mounted to the host and survives every container replacement and gateway restart, and no janitor sweep covers it, so Chrome's default (a fraction of free disk) made it the workspace's largest unbounded directory. The container also runs **without** `--disable-dev-shm-usage`: `--shm-size=2g` already sizes `/dev/shm`, and the flag merely redirected Chrome's shared memory to overlayfs — measured at ~1.3 MiB/s of writes on an idle browser.

**Sandbox in docker mode**: `browser.sandbox` is ignored — the container is the trust boundary; Chrome runs `--no-sandbox` because the slim base ships no SUID `chrome-sandbox`. Tightening would require a custom seccomp profile + a base image with the helper installed.

**Container lifecycle**: one container per Baybo process at a time (the watchdog replaces it on death), named `baybo-browser-<pid>-<rand6>`, labelled `baybo.role=browser-sidecar` + `baybo.pid=<pid>`. `docker run` is **not** invoked with `--rm` (so a startup crash leaves logs fetchable via `docker logs`). A container is created on **first browser use**, not per gateway process, so a boot that never browses creates none — read the `baybo.pid` sweep contract with that in mind. Cleanup: success-path `stop()` (`docker stop -t 5` + `docker rm -f`) followed by `clearContainerChromeLocks()`, failure-path force-remove, and the next-boot `sweepStaleContainers()` for `kill -9` cases. The lock sweep exists because `docker stop` never gives the container's Chrome a clean exit, so its `Singleton*` symlinks survive in the bind-mounted profile and every following boot used to log a `clearing stale Chrome lock` line on the way up. It runs only after the container is confirmed gone and only when the `SingletonLock` target's hostname half is *not* this host's — a guard kept deliberately even though the container is already removed, because it makes the sweep provably incapable of deleting a lock held by a live host Chrome sharing the same `browser.profile_dir`. Host mode is not swept: CDDM owns that Chrome and its exit is never observed, so the boot-time live-PID check remains the right handling there. The sweep keys off `baybo.pid` being alive — note that `process.kill(pid, 0)` raising `EPERM` means the process *exists* under another uid, so `isPidAlive` returns true there; reading it as dead would force-remove a running sidecar's container. Images are swept too (`sweepStaleImages`, after each spawn): the tag is a content hash of `Dockerfile` + `entrypoint.sh`, so every edit mints a fresh ~1.3 GB image that nothing would otherwise reclaim. It drops unreferenced `baybo-browser:*` images past `STALE_IMAGE_MAX_AGE_DAYS`, never the tag currently running. Containers and images from before the `aura`→`baybo` rename carry `aura.role` / `aura-browser:*` and are invisible to both sweeps by design — remove those by hand rather than teaching the sweep a legacy name it would carry forever. Inside the container Chrome listens on loopback only (Chrome 134+ silently ignores `--remote-debugging-address=0.0.0.0` for DNS-rebinding protection); a `socat 0.0.0.0:9223 → 127.0.0.1:9222` relay forwards the published port. CDP publishes on `127.0.0.1::9223` (ephemeral host port).

**Profile portability**: `browser.profile_dir` is bind-mounted at `/data/profile`; container runs `--user $(id -u):$(id -g)` so files round-trip cleanly between host-headless and docker modes under the same operator UID.
